## КОНТЕКСТ И ВЫВОДЫ ИЗ УЖЕ ИЗУЧЕННОГО

`WORK-HUNTER` сейчас задуман правильно: это private local-first tool с SQLite, локальными секретами, UI, MCP, HH flows, apply plans, approvals, events, templates, blacklist, external API/session recon и safety gates. Но сейчас он перегружен: есть много модулей, но нет одного железобетонного вертикального сценария. README прямо фиксирует, что часть HH/MCP путей ещё plan/dry-run oriented, `init` должен стать richer doctor/bootstrap, provider routing надо чистить, UI status нужен богаче.

Официальный HH API требует OAuth access token для методов с авторизацией. Access token передаётся как `Authorization: Bearer ACCESS_TOKEN`, а `/me` удобен для проверки токена. Значит для стабильной основы нужен API transport с refresh/preflight, а не попытки парсить всё из HTML.

`hh-applicant-tool` устроен как API-first:
- Playwright нужен для login/OAuth code.
- OAuth code меняется на access/refresh token.
- `ApiClient` работает с `https://api.hh.ru/`.
- `/vacancies` и `/resumes/{id}/similar_vacancies` дают поиск.
- обычный отклик идёт через `POST /negotiations`.
- cookies/web нужны для тестов, captcha/challenge, некоторых HTML-only действий.
- один `requests.Session` несёт и cookies, и API-контекст.

`hh-ai-responder` устроен как web-first:
- пользователь экспортирует `cookies.txt`;
- search URL копируется из HH UI;
- search params берутся из URL;
- резюме вытаскиваются из `/applicant/resumes` embedded JSON;
- вакансии вытаскиваются из `/search/vacancy` embedded JSON;
- отклик идёт через `/applicant/vacancy_response/popup` с `_xsrf`, `resume_hash`, `vacancy_id`, `letter`;
- чаты идут через `chatik.hh.ru` с cookies + XSRF;
- это быстро стартует, но зависит от HTML/внутренних web endpoints.

`work-optimization` важен как управленческая модель:
- проект лучше воспринимать как `automation worker`, а не как “самостоятельный бог-агент”;
- AI и агентный слой вспомогательные;
- deterministic commands должны быть ядром;
- agent читает digest/review и помогает выбирать стратегию;
- cron/systemd запускают повторяемые safe-операции;
- новый search сначала dry-run;
- массовые ответы работодателям не отправляются без review;
- preflight/digest/review endpoints делают систему управляемой.

## ЕДИНАЯ ДОКТРИНА ПРОДУКТА

`WORK-HUNTER` должен быть **локальным штабом поиска работы**, а не SaaS, не ботнет откликов, не хаотичный RPA и не копия upstream. Он должен:

1. Работать с личными аккаунтами пользователя и локальными секретами.
2. Давать сильный API-first контур для HH.
3. Иметь web/cookie fallback только там, где API не даёт возможности.
4. Нормализовать вакансии из разных источников в одну SQLite-модель.
5. Отделять поиск, планирование, подтверждение и отправку.
6. Делать dry-run нормой, а live action — явным событием.
7. Показывать причины каждого skip/block/error.
8. Давать агенту инструменты анализа и подготовки, но не позволять молча отправлять реальные заявки без политики и аудита.
9. Помогать против ATS за счёт честной адаптации резюме/писем/ключевых слов, а не за счёт выдуманных фактов.
10. Быть предсказуемым: каждая команда должна иметь понятный ввод, вывод, status, counters, trace id, logs.

```text
  ├── Source Registry
  ├── Transport Registry
  │     ├── HH API Transport          ← default для HH
  │     ├── HH Web Transport          ← fallback для tests/chat/search-url
  │     ├── External Session Transport
  │     └── Public Fetch Transport
  ├── Normalization
  ├── Scoring/Fit/ATS
  ├── Application Planner
  ├── Approval Queue
  ├── Operation Runner
  ├── Scheduler
  ├── Web Cockpit
  └── MCP/Agent API
```

Маршрутизация HH должна быть такой:

```text
/me                                     → HH API
/resumes/mine                           → HH API
/resumes/{id}                           → HH API
/vacancies                              → HH API
```

Никаких “магических попыток всего подряд”. У каждого действия должен быть `capability`, `preferred_transport`, `fallback_transport`, `requires_auth`, `requires_confirmation`, `risk_flags`, `blocked_reason`.

## DOCTOR / PREFLIGHT

`doctor` — главная команда проекта.

Она проверяет:

- Python version;
- installed package;
- missing deps (`requests`, `mcp`, `starlette`, optional `playwright`, `beautifulsoup4`);
- config path;
- DB path;
- migration state;
- active profile exists;
- profile has queries/roles/skills;
- enabled sources;
- HH API auth:
  - access token exists;
  - `/me` works;
  - refresh token exists;
  - refresh works or not;
  - resumes exist;
- HH Web:
  - cookie file exists;
  - `_xsrf`;
  - `/applicant/resumes` parse;
- AI:
  - sections configured;
  - endpoint test optional;
- UI:
  - bind host is local;
  - port availability;
- MCP:
  - server import works;
- secrets:
  - no `.work-hunter` tracked by git;
  - no token patterns in staged diff;
- upstream:
  - optional `hh-applicant-tool` available;
  - version;
  - config dir.

Вывод должен быть machine-readable JSON и human readable text.

```bash
work-hunter doctor --json
work-hunter doctor
```

Human output:

```text
WORK-HUNTER DOCTOR

Core:
  Python: ok 3.11
  DB: ok, migrations 12/12
```

## HH SEARCH ДОЛЖЕН БЫТЬ РАЗДЕЛЁН С CAMPAIGN

Сейчас `hh-search-campaign-plan` делает поиск и сразу строит apply plans. Это слишком тяжело.

Разделить:

```bash
work-hunter hh search --text "python backend" --area 1 --limit 100 --save
work-hunter hh campaign plan --from-search-run RUN_ID --resume-id RESUME_ID --min-score 50
work-hunter hh campaign confirm --run-id RUN_ID --confirm
```

`hh search`:
- только ищет;
- импортирует вакансии;
- сохраняет search_run;
- не вызывает `suitable_resumes` на каждую вакансию;
- не готовит письма;
- не отправляет.

`campaign plan`:
- берёт сохранённые jobs;
- score;
- фильтрует;
- делает apply plan;
- показывает ready/skipped/error;
- не отправляет.

`campaign confirm`:
- отправляет только `ready`;
- требует `--confirm`;
- rate limit;
- пишет result по каждой вакансии.

Live action — это всё, что может:
- отправить отклик;
- отправить сообщение работодателю;
- закрыть/скрыть переговоры;
- занести работодателя в blacklist;
- изменить резюме;
- отправить email;
- сделать external mutating request.

Для live action обязательно:

```json
{
  "requires_confirmation": true,
  "approval_id": 123,
  "preview": "...",
  "risk_flags": [],
  "policy": "safe",
  "confirmed_by_user": true
}
```

MCP/agent не получает bypass.

## AI / LLM

AI — это функция генерации/оценки, а не исполнитель.

Разделить AI providers:

```text
ai.cover_letter
ai.reply
ai.vacancy_filter
ai.ats
ai.captcha_optional
```

Единый OpenAI-compatible client:
- base_url;
- api_key;
- model;
- temperature;
- max_tokens;
- retry;
- rate_limit;
- timeout;
- proxy.

AI outputs должны быть typed:
- `CoverLetterDraft`;
- `ReplyDraft`;
- `VacancyFilterDecision`;
- `ATSAnalysis`;
- `TestAnswerDraft`.

JSON parsing:
- strict mode where needed;
- fallback to needs_review;
- raw saved redacted;
- no silent fake.

## КАЧЕСТВО ОТКЛИКОВ

Система должна помогать попасть на интервью, а не просто спамить.

Для каждой заявки:
- проверить fit;
- проверить stop words;
- проверить salary/location;
- проверить test/manual form;
- проверить duplicate employer;
- подготовить короткое письмо;
- сохранить, какая версия письма была отправлена;
- позже связать с результатом переговоров.

Метрики:

```text
applications_sent
responses_received
invitations
rejections
silent_after_3_days
silent_after_7_days
interviews
offers
```

Dashboard должен показывать conversion по search presets.

## СТРАТЕГИИ ПОИСКА

Сделать search strategy engine:

```json
{
  "name": "backend-python-remote",
  "queries": [
    {"text": "python backend", "area": ["1"], "schedule": "remote"},
    {"text": "fastapi", "area": ["1"], "schedule": "remote"},

  ],
  "exclude": "junior|стаж[её]р|bitrix|1с",
  "min_score": 50,
  "daily_limit": 40,
  "dry_run_required": true
}
```

Команды:

```bash
work-hunter strategy list
work-hunter strategy run backend-python-remote --dry-run
work-hunter strategy run backend-python-remote --confirm
work-hunter strategy report backend-python-remote
```

## НЕЛЬЗЯ

- Нельзя делать вид, что HTML parser нашёл 0 вакансий, если на самом деле пришла login/challenge page.
- Нельзя отправлять live apply из команды, которая называется `plan`.
- Нельзя отправлять live reply без preview.
- Нельзя хранить HAR/cookies/tokens в repo.
- Нельзя делать silent fallback с API на web send.
- Нельзя маскировать `invalid token` как generic error.
- Нельзя считать AI decision достаточным для live send.
- Нельзя поддерживать два несовместимых HH клиента.
- Нельзя плодить команды без `doctor` и тестов.
- Нельзя обещать direct apply для non-HH, пока нет проверенного adapter contract.

## ИТОГОВЫЙ ОБРАЗ

Идеальный `WORK-HUNTER` — это не “бот, который жмёт всё подряд”. Это кабина:

```text
[Auth OK] [Sources OK] [Search Presets] [Jobs] [Scores] [Plans] [Approvals] [Sent] [Negotiations] [Digest]
```

Пользователь утром видит:
- авторизация жива;
- резюме подняты;
- найдено N вакансий;
- M хороших;
- K готовы к отклику;
- X требуют review из-за теста/формы;
- Y работодателей ждут ответа;
- вот письма;
- вот риски;
- нажми confirm или отклони.

Агент помогает:
- объяснить ошибки;
- предложить поисковые запросы;
- улучшить письмо;
- подсказать, почему вакансия не fit;
- подготовить follow-up;
- но не устраивает бесконтрольный live хаос.

## ФИНАЛЬНЫЙ ПРИКАЗ АГЕНТУ

Не пытайся сделать “ещё одну фичу”. Сначала собери позвоночник.

Когда сомневаешься, выбирай:
- API вместо HTML;
- plan вместо live;
- typed status вместо строки;
- doctor вместо гадания;
- source capability вместо hardcode;
- fixture test вместо ручной надежды;
- redaction вместо удобного debug;
- explicit confirm вместо “ну пользователь же хотел”.

Результат должен быть скучно надёжным: запустил doctor, увидел проблему, починил auth, нашёл вакансии, получил план, подтвердил, отправил, увидел отчёт.
