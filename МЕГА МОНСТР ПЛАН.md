# МЕГА МОНСТР ПЛАН: Work Hunter до состояния «как апстримы, но лучше»

> Этот документ — единый большой план-договор для доработки `WORK-HUNTER`.  
> Не делить на «фазы ради фаз». Двигаться по зависимостям, но держать в голове одну цель: **локальный job-search command center, где deterministic worker делает действия, а агент помогает выбирать стратегию, объяснять, готовить тексты, анализировать результаты и не ломать аккаунт**.

---

## МЕГА-ПРОМПТ ДЛЯ КОДОВОГО АГЕНТА

Ты работаешь в приватном репозитории `Kiwunaka/WORK-HUNTER`. Твоя задача — превратить текущий набор модулей в цельный локальный инструмент для поиска работы, откликов, резюме, переписок и агентного контроля. Работай как senior Python/product engineer: сначала читай код и тесты, потом меняй минимально, но системно. Не переписывай всё с нуля, пока не доказал, что существующий модуль нельзя спасти.

Нельзя коммитить секреты, cookies, HAR, токены, `.env`, SQLite, логи, приватные профили, дампы браузера. Любые auth/cookie/token значения в логах, UI, API и тестах маскируй. Все реальные действия с аккаунтами, откликами, чатами и резюме должны иметь безопасный контур: preflight → dry-run/plan → review → explicit confirm/live. Автоматизация должна быть локальной, наблюдаемой, ограниченной и обратимой. Никаких «сам решил и массово отправил» без заранее разрешённого пресета и лимитов.

Главный архитектурный выбор: **HH API/OAuth — основной транспорт; cookie/web — fallback только для того, чего API не покрывает**. Поиск через API, резюме через API, `/me` через API, обычный отклик через API `/negotiations`, переговоры через API там, где хватает. Web/cookie использовать для XSRF, web popup, тестов, браузерного search URL, `chatik.hh.ru`, диагностики HTML/challenge, но не как хаотичный дефолт. Для каждого действия должна быть таблица маршрутизации: `action → preferred_transport → fallback_transport → required_credentials → safety_gate → audit_event`.

Держи ориентиры апстримов:
- `s3rgeym/hh-applicant-tool`: API-first, Playwright OAuth login, Android-like UA, общий `requests.Session`, токены в config, cookies в cookies.txt, SQLite, search через `/vacancies` или `/resumes/{id}/similar_vacancies`, обычный apply через `/negotiations`, web popup только для тестов/сложных форм.
- `s3rgeym/hh-ai-responder`: cookie/web-first, быстрый запуск через `cookies.txt` и search URL из браузера, `resume_hash`, `_xsrf`, HTML embedded JSON, `/applicant/vacancy_response/popup`, `chatik.hh.ru`.
- `orelkrylatiy/work-optimization`: оформленная агентная модель: это automation worker, не «бесконтрольный автономный агент»; есть preflight/digest/review, agent-friendly JSON, cron/systemd scheduling, safe dry-run → live, профили, web admin, docs, LLM setup, decision matrix.

Твоя цель лучше апстримов:
- единый транспортный слой вместо разрозненных клиентов;
- нормальный bootstrap/doctor;
- OAuth login/import/refresh без ручной правки JSON;
- cookie import и browser login как поддерживаемый fallback;
- typed models и event log;
- source adapters для HH, Habr, GeekJob, Getmatch, Telegram и прочих, но с честными capabilities;
- scoring, ATS-fit, cover letters и resume tailoring только на основе правдивого профиля пользователя;
- agent API/MCP/UI как supervisory cockpit;
- тесты на каждую опасную ветку;
- понятные CLI-команды;
- документация, которая объясняет happy path за 5 минут.

## ИСТОЧНИКИ И ВЫВОДЫ, КОТОРЫЕ НЕЛЬЗЯ ИГНОРИРОВАТЬ

Официальная модель HH API: большинство запросов требует `access_token`; токен передаётся как `Authorization: Bearer ACCESS_TOKEN`; `/me` является удобной проверкой токена. Документация также указывает, что для авторизации нужно использовать домен `hh.ru`, а не `m.hh.ru`.

Официальные методы по вакансиям включают поиск вакансий, получение вакансии и похожие вакансии. Короткое представление вакансии содержит поля, которые надо использовать в safety/filtering: `has_test`, `response_url`, `alternate_url`, `apply_alternate_url`, `relations`, `response_letter_required`, `archived`, salary, area, employer.

`hh-applicant-tool` доказывает рабочую API-first модель: Playwright используется для получения OAuth code через Android-like flow; затем code меняется на access/refresh token; `ApiClient` ходит в `https://api.hh.ru/`, автоматически refresh-ит токен и использует общий `requests.Session`; обычный apply идёт через `/negotiations`; web cookie/XSRF используется для тестов и HTML fallback.

`hh-ai-responder` доказывает рабочую web-first модель: можно быстро стартовать от `cookies.txt` и URL поиска из интерфейса HH; из HTML страниц вытаскиваются embedded JSON блоки; используется `resume_hash`, `_xsrf`, `/applicant/vacancy_response/popup` и `chatik.hh.ru`. Это полезный fallback, но он более хрупкий из-за зависимости от HTML/внутренних web endpoint’ов.

`work-optimization` добавляет важный продуктовый вывод: инструмент лучше считать `automation worker`, где cron/systemd запускает предсказуемые команды, а LLM/агент не имеет бесконтрольного live-control. Агент должен читать preflight/digest/review, помогать с search-параметрами, письмами, follow-up и разбором логов, но новый поиск сначала идёт dry-run, а массовые ответы работодателям требуют review.

## ЦЕЛЕВАЯ ФОРМУЛА ПРОДУКТА

`Work Hunter` — это локальный приватный центр управления поиском работы:

- собирает вакансии из разных источников;
- нормализует их в одну модель;
- оценивает fit относительно профилей пользователя;
- готовит правдивые резюме/письма/ATS-summary;
- запускает безопасные HH workflows;
- ведёт локальное состояние: найдено, пропущено, откликнулся, ответили, отказ, follow-up, blacklist;
- даёт агенту инструменты, но не отдаёт ему бесконтрольную кнопку массовой отправки;
- показывает всё в CLI, local UI, MCP/API;
- хранит секреты локально и не печатает их.

Главный happy path должен быть таким:

```text
install works
  → init/doctor works
  → profile exists
  → auth/import works
  → hh /me works
  → resumes sync works
  → search works
  → scoring works
  → plan works
  → dry-run report is understandable
  → explicit confirm sends limited batch
  → digest shows result
  → review inbox suggests next actions
```

Если этот путь не зелёный, все «комбайны всего всего» считаются вторичными.

### 2. Transports as first-class objects

Нужен единый интерфейс:

```python
class TransportHealth(TypedDict):
    name: str
    configured: bool
    authorized: bool
    can_refresh: bool
    identity: dict[str, Any] | None
    expires_at: str | None
    diagnostics: list[str]
    actions: list[str]

class HHApiTransport:
    def health(live: bool = False) -> TransportHealth: ...
    def request_json(method, path, *, params=None, data=None, json=None): ...
    def refresh(): ...
    def whoami(): ...
    def search_vacancies(params): ...
    def list_resumes(): ...
    def apply(vacancy_id, resume_id, message): ...

class HHWebTransport:
    def health(live: bool = False) -> TransportHealth: ...
    def load_cookies(): ...
    def xsrf_token(): ...
    def get(path_or_url): ...
    def post_form(path_or_url, data, referer): ...
    def search_by_url(search_url, page): ...
    def apply_popup(vacancy_id, resume_hash, letter, test_payload=None): ...
```

`HHApplyClient`, `HHApiSession`, `HHBrowserSession`, `HHWebActions` должны перестать быть параллельными несовместимыми мирами. Либо заменить `HHApplyClient` на `HHApiTransport`, либо сделать `HHApplyClient` тонкой обёрткой над ним.

### 3. Action routing table

В коде и документации должна быть явная таблица:

| Action | Preferred | Fallback | Required auth | Safety |
|---|---|---|---|---|
| auth status | API | web cookies health | access token / cookies | safe |
| `/me` | API | none | access token | safe |
| list resumes | API | web `/applicant/resumes` parse | token or cookies | safe |
| touch/boost resume | API if supported/reliable | web `/applicant/resumes/touch` | token or cookies+xsrf | confirm or preset |
| vacancy search by params | API `/vacancies` | web search URL | token optional/app token or cookies | dry-run by default |
| vacancy search by copied HH URL | web | API params converter | cookies or anonymous web | dry-run |
| vacancy detail | API `/vacancies/{id}` | web vacancy page parse | none/token/cookies | safe |
| ordinary apply | API `/negotiations` | web popup | token or cookies+xsrf | plan + confirm |
| apply with test | web popup | manual review | cookies+xsrf | review required |
| chat list/reply | API if enough | `chatik.hh.ru` | token/cookies+xsrf | review + confirm |
| cleanup/blacklist | API | web | token/cookies | confirm |
| external platform apply | none | session adapter only after recon | personal session | manual review |

## BOOTSTRAP/DOCTOR: ОБЯЗАТЕЛЬНАЯ СЕРДЦЕВИНА

`init` должен не просто создать config, а провести пользователя:

```bash
work-hunter init --interactive
```

Проверки:
- Python version;
- installed package editable or wheel;
- runtime dependencies: requests, starlette, mcp, optional playwright, optional bs4/lxml;
- config path;
- db path;
- writable data dir;
- profile exists;
- active HH account exists;
- token present;
- refresh token present;
- `/me` works if `--live`;
- cookies file exists;
- XSRF can be extracted if cookies configured;
- resumes sync works if `--live`;
- search sample works if `--live`;
- UI port available;
- no secrets in git tracked/staged files;
- no `.work-hunter` accidentally committed.

Output JSON:

```json
{
  "status": "ok|warning|blocked",
  "checks": [
    {"id": "python", "status": "ok", "message": "..."},
    {"id": "hh_api_auth", "status": "blocked", "action": "work-hunter hh auth login"}
  ],
  "next_actions": []
}
```

Exit codes:
- `0` ok;
- `1` warning but usable;
- `2` blocked;
- `3` config/data corruption.

## HH AUTH: СДЕЛАТЬ КАК НАДО

Нужны три рабочих способа авторизации.

### OAuth/browser login

Повторить идею `hh-applicant-tool`, но чище:
- Playwright optional dependency;
- открыть OAuth URL;
- использовать нормальный client id/secret из config или user-provided app;
- не хардкодить чужие секреты как единственный вариант;
- поддержать manual redirect paste;
- поймать OAuth code;
- exchange code → token;
- сохранить token в active account;
- сохранить HH cookies в `cookies.txt`;
- маскировать всё в логах;
- сохранить auth event.

Команды:

```bash
work-hunter hh auth login --profile default --account default
work-hunter hh auth login --manual-code
work-hunter hh auth login --no-headless
```

### Token import

Поддержать импорт из `hh-applicant-tool` config:

```bash
work-hunter hh auth import-token-file ./config/config.json --format hh-applicant-tool
```

Должно вытащить:
- `token.access_token`;
- `token.refresh_token`;
- `token.access_expires_at`;
- `client_id`;
- `client_secret`;
- `user_agent`;
- не печатать значения.

### Cookies import

Поддержать Netscape `cookies.txt` и Playwright JSON cookies:

```bash
work-hunter hh auth import-cookies ./cookies.txt --format netscape
work-hunter hh auth import-cookies ./cookies.json --format playwright
```

Должно:
- оставить только `hh.ru` и поддомены;
- проверить `_xsrf`;
- проверить `redirect_host`;
- сделать web health check;
- сохранить в `.work-hunter/hh/accounts/<account>/cookies.txt`.

### Refresh

`refresh-token` должен:
- использовать active account backend;
- обновлять config atomically;
- сохранять refresh token, если сервер выдал новый;
- не ломать account, если refresh failed;
- писать audit event.

## HH API WORKFLOWS

### Search

API search должен быть отдельной командой и сервисом, не «побочным эффектом campaign plan».

Правила:
- `per_page <= 100`;
- `limit` реализуется через пагинацию;
- `page` и `pages` нормализуются;
- параметры проходят allowlist;
- массивные параметры (`area`, `professional_role`, `industry`, `employment`, `search_field`) правильно кодируются;
- `only_with_salary` нормализуется в bool/строку согласно API;
- результат сохраняется как `hh_search_run` и `jobs`;
- каждый item содержит raw payload redacted;
- если API вернул ошибку — показать понятную причину.

Команды:

```bash
work-hunter hh search --text "python backend" --area 1 --schedule remote --limit 100 --save
work-hunter hh search --preset backend-remote --save
work-hunter hh search --from-profile --save
```

### Search URL

Web search URL нужен как отдельный режим:
- принимает скопированный URL из браузера HH;
- сохраняет query params;
- может либо ходить web fallback, либо конвертировать часть параметров в API;
- если HTML marker не найден, не возвращает «0 вакансий», а диагностирует challenge/markup/login;
- сохраняет HTML fingerprint без секретов.

```bash
work-hunter hh search-url "https://hh.ru/search/vacancy?..." --limit 100 --save
```

### Resumes

- `resumes list --sync` через API `/resumes/mine`;
- `resumes boost` через API, если есть валидный endpoint; иначе web fallback `/applicant/resumes/touch`;
- не поднимать резюме чаще разрешённого лимита;
- хранить `last_boost_at`, `next_allowed_at`;
- если web fallback требует XSRF/cookies — явно сказать.

### Apply planning

План не отправляет. Он:
- берёт jobs из search run или storage;
- проверяет `relations`;
- проверяет `archived`;
- проверяет `response_letter_required`;
- проверяет `has_test`;
- проверяет `response_url`;
- проверяет blacklist/skip history;
- подбирает resume;
- генерирует/подставляет letter;
- запускает scoring/AI filter, если включено;
- пишет campaign items со статусами `ready`, `skipped`, `needs_review`, `blocked`, `error`.

Статусы:
- `ready_api_apply`;
- `ready_web_apply`;
- `needs_test_review`;
- `needs_manual_form`;
- `already_applied`;
- `archived`;
- `blacklisted`;
- `below_min_score`;
- `ai_rejected`;
- `no_resume`;
- `auth_missing`;
- `challenge_required`;
- `error`.

### Apply confirm

Confirm:
- берёт только готовые items;
- требует `--confirm`;
- применяет лимиты: total, per employer, per minute, per day;
- случайный или фиксированный delay configurable;
- stop on captcha/challenge/429/403/auth error;
- stop on negotiations limit;
- пишет application and operation logs;
- idempotent: не отправлять повторно, если application уже есть.

Обычный API apply:
```http
POST /negotiations
resume_id=<id>
vacancy_id=<id>
message=<letter>
```

Web apply fallback:
```http
POST /applicant/vacancy_response/popup
_xsrf=<token>
vacancy_id=<id>
resume_hash=<hash>
letter=<letter>
ignore_postponed=true
```

Тесты/анкеты:
- по умолчанию `needs_review`;
- AI может подготовить draft, но не отправлять без confirm;
- не обходить challenge/captcha автоматически по умолчанию;
- unknown fields → stop.

- `skip_rejection`;
- `wait_recent_application`;
- `wait_recent_activity`;
- `manual_review`.

Факторы:
- кто писал последним;
- сколько дней прошло;
- статус;
- есть ли приглашение;
- есть ли отказ;
- была ли уже попытка follow-up;
- работодатель/вакансия в blacklist;
- есть ли контактные данные.

### Reply plan/confirm

- AI может написать draft;
- draft строится на истории переписки, вакансии, резюме и контактах пользователя;
- `reply-confirm` требует confirm;
- массовый reply без review запрещён;
- для `chatik.hh.ru` нужен web transport и XSRF;
- для API messages использовать API, если endpoint работает.

## AGENT LAYER: НЕ БЕСКОНТРОЛЬНЫЙ ПИЛОТ, А SUPERVISOR

Агент нужен для:
- объяснить, почему auth сломан;
- выбрать безопасный search preset;
- сравнить выдачу dry-run;
- предложить фильтр исключений;
- подготовить письма;
- подготовить ответы;
- подсветить риски;
- сделать digest;
- показать, что сегодня уже достаточно откликов.

Агент не должен:
- запускать новый live search без dry-run;
- массово отвечать в чатах без review;
- менять токены/секреты без явной команды;
- скрывать ошибки;
- отправлять заявки, если есть challenge/captcha/unknown form;
- выдумывать опыт пользователя.

### Agent API

Local HTTP endpoints:

```http
GET  /api/agent/preflight?live=true
GET  /api/agent/digest
GET  /api/agent/review-negotiations
POST /api/agent/run
POST /api/agent/approve/{approval_id}
POST /api/agent/reject/{approval_id}
GET  /api/jobs
GET  /api/jobs/{id}
GET  /api/hh/search-runs
GET  /api/hh/campaign-runs
GET  /api/hh/inbox
POST /api/hh/inbox/{id}/reply-plan
POST /api/hh/inbox/{id}/reply-confirm
```

`/api/agent/run` принимает только allowlisted operations и presets:

```json
{
  "operation": "hh.apply.plan",
  "preset": "backend_remote",
  "dry_run": true,
  "profile": "default",
  "account": "default"
}
```

Live operations требуют:
- `confirm: true`;
- preset id;
- max count;
- audit reason;
- no pending high-risk flags.

### MCP

MCP tools должны повторять безопасный API:
- `work_hunter_preflight`;
- `work_hunter_digest`;
- `work_hunter_search_hh`;
- `work_hunter_plan_hh_apply`;
- `work_hunter_confirm_hh_apply`;
- `work_hunter_review_inbox`;
- `work_hunter_draft_reply`;
- `work_hunter_confirm_reply`.

Каждый MCP call пишет `agent_runs`.

## SCORING / ATS / RESUME TAILORING

Цель — помогать пройти фильтры, но не превращать профиль в фантазию.

### Profile model

```json
{
  "summary": "",
  "roles": [],
  "skills": {
    "must_have": [],
    "nice_to_have": [],
    "avoid": []
  },
  "experience": [],
  "salary": {},
  "locations": [],
  "remote": true,
  "links": {},
  "facts": []
}
```

Все генерации должны ссылаться только на `facts`, `experience`, `skills`.

### Scoring

Компоненты:
- role match;
- skills match;
- seniority match;
- salary match;
- location/remote;
- stop words;
- employer blacklist;
- response competition if available;
- test/manual form risk;
- novelty/freshness.

Score должен быть explainable:

```json
{
  "total": 78,
  "reasons": [
    {"factor": "skills", "score": 30, "message": "Python/FastAPI/Postgres match"},
    {"factor": "stop_words", "score": -10, "message": "mentions Bitrix"}
  ]
}
```

### ATS outputs

- generate ATS summary for a vacancy;
- suggest truthful resume keyword additions;
- suggest cover letter;
- suggest interview prep;
- never invent job titles, employers, years, credentials.

## SOURCES BEYOND HH

HH — главный рабочий контур. Остальные источники должны быть honest adapters.

Для каждого source:

```python
class SourceCapabilities(TypedDict):
    search: Literal["api", "public_html", "frontend_json", "rss", "manual", "unsupported"]
    detail: ...
    apply: Literal["api", "external_page", "email", "personal_auth_recon", "unsupported"]
    auth: Literal["none", "oauth", "cookie", "browser_session", "manual"]
    reliability: Literal["stable", "fragile", "experimental"]
```

Не писать «полная автоматизация», если source умеет только открыть страницу.

### External sessions

HAR/API recon оставить как лабораторию:
- только для личных аккаунтов пользователя;
- read-only по умолчанию;
- mutating calls только `--real --unsafe-lab --confirm`;
- redaction обязательна;
- никаких секретов в reports.

## SECURITY / SAFETY

Не обсуждать это как «лишнюю этику» — это защита аккаунта и данных.

- local-first;
- secrets never logged;
- cookies never printed;
- HAR redacted;
- challenge/captcha stops by default;

- no use of other people’s sessions;
- explicit confirm for mutating calls;
- rate limits;
- idempotency;
- blacklist respected;
- duplicate companies controlled;
- stop on suspicious failures.

Sensitive patterns:
- `Authorization`;
- `access_token`;
- `refresh_token`;
- `client_secret`;
- cookies;
- `_xsrf`;
- `sk-*`;
- Telegram tokens;
- SMTP passwords;
- HAR request/response bodies with auth.

```bash
python -m venv .venv
. .venv/bin/activate
```

```bash

work-hunter hh whoami --json
work-hunter hh auth refresh --json
```
Показывает понятные статусы, не печатает секреты.

### Search
```bash
work-hunter hh search --text "python backend" --area 1 --limit 120 --save --json
```
Делает пагинацию, сохраняет run, не ломается на `limit > 100`.

```bash
work-hunter hh apply plan --search-run <id> --resume-id <id> --limit 50 --json
```

Ничего не отправляет, объясняет каждый skip/ready.

```bash
work-hunter hh apply confirm --campaign-run <id> --limit 10 --confirm --json
```

### Inbox
```bash
work-hunter hh inbox sync --json

```
Показывает, где ответить, где ждать, где отказ.

```bash
work-hunter agent preflight --live --json
work-hunter agent digest --json
```
Достаточно, чтобы агент понял состояние без чтения логов руками.

### UI
```bash
work-hunter ui
```
Dashboard показывает auth, resumes, search runs, campaigns, inbox, errors.

### Safety
- при challenge/captcha unknown state → stop;
- при missing token → action hint;
- при broken cookies → action hint;
- при token invalid + refresh token → suggest refresh;
- при no refresh → suggest login;
- при high-risk campaign → needs_review;
- secrets masked everywhere.

## ИДЕАЛЬНАЯ МЕНТАЛЬНАЯ МОДЕЛЬ

`hh-applicant-tool` — двигатель API.  
`hh-ai-responder` — быстрый web fallback.  
`work-optimization` — agent/scheduling/product discipline.  
`WORK-HUNTER` должен стать cockpit, который объединяет это в локальную систему:

```text
API-first engine
+ web fallback where needed
+ local state
+ explainable scoring
+ safe planning
+ explicit live confirmation
+ inbox intelligence
+ supervisory agent
+ UI/MCP
+ docs/tests/observability
```

Главный критерий: пользователь запускает `doctor`, видит понятную правду, нажимает dry-run, понимает результат, подтверждает ограниченную отправку, потом видит digest и не теряет ответы работодателей.

Если после доработок нужно объяснять «ну оно работает, если руками поправить config и не трогать эти команды» — план не выполнен.
